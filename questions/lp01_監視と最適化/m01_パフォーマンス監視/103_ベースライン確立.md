# 監視103 — ベースラインメトリックの確立

> 対応ユニット: [ベースライン メトリックを確立する](https://learn.microsoft.com/ja-jp/training/modules/describe-performance-monitoring/4-establish-baseline-metrics)

## 問題 1

ベースラインメトリックの目的として最も適切な説明はどれですか？

- A. パフォーマンス問題が発生したときに即座に修正するための手順書
- B. 通常状態のパフォーマンスを把握し、正常からの逸脱を検知するためのデータ基準
- C. Azure が自動的に収集するアラートのしきい値の初期設定値
- D. 本番環境に適用する前にテスト環境で確認するためのスクリプト集

<details>
<summary>解答・解説</summary>

**解答:** B

ベースラインとは、アプリケーションやサーバーの通常状態を理解するためのデータ測定値のコレクションです。長期にわたって収集することで、通常からの変化（異常）を特定できます。ベースラインがないと、問題が発生しても正常範囲なのか異常なのか判断できません。

| 選択肢 | 説明 | 正否 |
|---|---|---|
| A. 修正手順書 | ベースラインはデータ基準であり手順書ではない | ❌ |
| B. 通常状態のデータ基準 | ベースラインの正確な定義 | ✅ 正解 |
| C. Azure の自動初期設定値 | Azure が自動設定するものではない | ❌ |
| D. テスト環境用スクリプト | ベースラインとは別の概念 | ❌ |

</details>

## 問題 2

SQL Server の待機統計を確認するために使用する動的管理ビュー（DMV）はどれですか？

- A. `sys.dm_exec_query_stats`
- B. `sys.dm_os_wait_stats`
- C. `sys.dm_io_virtual_file_stats`
- D. `sys.dm_os_volume_stats`

<details>
<summary>解答・解説</summary>

**解答:** B

`sys.dm_os_wait_stats` は、スレッドがリソースの待機に費やした時間を種類別に追跡する DMV です。ベースラインと照合することで、CPU・I/O・ロックなどのボトルネックを特定できます。待機統計は Azure SQL プラットフォーム全体で使用できます。

| 選択肢 | 説明 | 正否 |
|---|---|---|
| A. dm_exec_query_stats | クエリの実行統計（CPU 時間・論理読み取り等） | ❌ |
| B. dm_os_wait_stats | 待機統計。ベースライン分析の重要な DMV | ✅ 正解 |
| C. dm_io_virtual_file_stats | データベース ファイルの I/O 統計 | ❌ |
| D. dm_os_volume_stats | ボリュームのストレージ統計 | ❌ |

</details>

## 問題 3

PerfMon カウンター `PhysicalDisk(_Total)\Avg. Disk sec/Read` について、通常の許容範囲として最も適切な説明はどれですか？

- A. 値は常に 0 ミリ秒でなければならない
- B. 通常は 20 ミリ秒以内が目安で、Premium Storage では 10 ミリ秒未満が期待される
- C. 100 ミリ秒以内であれば問題ない
- D. このカウンターの値は SQL Server のパフォーマンスとは無関係

<details>
<summary>解答・解説</summary>

**解答:** B

ディスク読み書きの平均待機時間は通常 20 ミリ秒以内であることが目安です。Azure Premium Storage を使用している場合は 10 ミリ秒未満の値が期待されます。これを超えている場合はストレージ サブシステムのボトルネックが疑われます。

| 選択肢 | 説明 | 正否 |
|---|---|---|
| A. 常に 0 ms | 物理的に不可能。0 は目標値ではない | ❌ |
| B. 20 ms 以内、Premium は 10 ms 未満 | 公式ドキュメントの目安値 | ✅ 正解 |
| C. 100 ms 以内 | 実際にはこの値ではパフォーマンス問題が発生する | ❌ |
| D. SQL と無関係 | I/O 待機は SQL のクエリ性能に直結する | ❌ |

</details>

## 問題 4

`SQLServer:Buffer Manager\Page Life Expectancy`（ページの平均寿命）カウンターの解釈として正しいものはどれですか？

- A. 300 秒を下回ると必ず深刻なメモリ不足を示す
- B. 値が高いほど常に良好で、低いほど常に問題がある
- C. 長期にわたって監視し、急激な低下をベースラインと比較して評価すべきメトリック
- D. Azure SQL Database では使用できない

<details>
<summary>解答・解説</summary>

**解答:** C

ページの平均寿命には「この値が正しい」という絶対基準はありません。サーバーのメモリ容量によって正常値が異なるためです。重要なのは長期的なベースラインを把握し、急激な低下が発生したときにその原因（不適切なクエリ・外部メモリ負荷・大規模な整合性チェックなど）を調査することです。

| 選択肢 | 説明 | 正否 |
|---|---|---|
| A. 300 秒以下で深刻 | 古い 32 ビット時代の基準。現在は適用されない | ❌ |
| B. 高いほど良い（絶対基準） | 絶対的な良し悪しはない。ベースラインとの比較が重要 | ❌ |
| C. 長期監視・急激低下に注目 | 正しいアプローチ | ✅ 正解 |
| D. Azure SQL で使用不可 | 使用可能 | ❌ |

</details>

## 問題 5

`System\Processor Queue Length` カウンターの値が継続的に 0 より大きい場合、何を示しますか？

- A. ディスク I/O のボトルネック
- B. SQL Server のメモリ不足
- C. CPU の負荷が高く、より多くの処理能力が必要な可能性がある
- D. ネットワーク帯域幅の不足

<details>
<summary>解答・解説</summary>

**解答:** C

Processor Queue Length はプロセッサ上の時刻を待機しているスレッドの数を示します。0 より大きい場合は CPU 負荷を示し、ワークロードがより多くの CPU から恩恵を受ける可能性があります。

| 選択肢 | 説明 | 正否 |
|---|---|---|
| A. ディスク I/O ボトルネック | PhysicalDisk カウンターで確認する指標 | ❌ |
| B. SQL Server のメモリ不足 | Page Life Expectancy やページ ファイルのカウンターで確認 | ❌ |
| C. CPU 負荷・処理能力不足の可能性 | Processor Queue Length の正しい解釈 | ✅ 正解 |
| D. ネットワーク帯域幅の不足 | ネットワーク カウンターで確認する指標 | ❌ |

</details>

## 問題 6

適切に構成された SQL Server では `Paging File(_Total)% Usage` カウンターの値について何が期待されますか？

- A. ピーク時に 50% 程度まで増加するが許容範囲
- B. メモリがディスクにページングされないため、値は低く安定しているべき
- C. このカウンターは SQL Server の監視には不要
- D. 値は常に 0 でなければならず、0 以外はシステム障害を示す

<details>
<summary>解答・解説</summary>

**解答:** B

適切に構成された SQL Server では、SQL Server のメモリがディスク上のページ ファイルに移動しません。このカウンターが高い場合は、SQL Server 以外のサービスがシステムメモリを消費し、OS がメモリをディスクにページングしていることを示す可能性があります。

| 選択肢 | 説明 | 正否 |
|---|---|---|
| A. 50% まで許容 | 高いページング使用率はパフォーマンス低下の原因 | ❌ |
| B. 低く安定しているべき | 正しい期待値。SQL Server は適切に設定されていればページングされない | ✅ 正解 |
| C. 監視不要 | 他サービスのメモリ圧迫を検知するために有用 | ❌ |
| D. 必ず 0 | 0 でなくても即障害ではないが、上昇には注意が必要 | ❌ |

</details>
